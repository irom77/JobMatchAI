# Tailor Resume for Job

Create a job-specific resume that presents the candidate's real experience in the most relevant order and language. Use the project-root `candidate_summary.txt` as the sole source of candidate facts. Keep it read-only during normal resume tailoring. Edit, replace, or append to it only when the user explicitly asks to update the source profile. Do not use LinkedIn or other candidate sources unless the user explicitly asks to add them. Do not invent or infer employers, dates, titles, education, skills, accomplishments, metrics, or credentials absent from the summary or explicitly supplied by the user.

## Workflow

1. Resolve the posting from whichever identifier the user provides: a direct job URL, a company and job title, or a saved `*-jobs.json` file (optionally with company/title or job ID). For a URL, retrieve the public posting using available browsing or page access. Do not bypass sign-in, access controls, or anti-bot protections. If the URL cannot be accessed, ask the user to paste the posting text or identify a matching saved job record. If company and title identify multiple postings, ask which one. Read only the matching record and necessary metadata.
2. Before drafting or preparing an application, check `job-applications/applications.json`. If it does not exist, treat the tracker as empty. Match a prior application to the same job by requisition/job ID or canonical posting URL (remove tracking query parameters); when neither is available, use normalized company, title, and location. If Gmail is connected, also search for an application/confirmation email matching the role and company. A tracker entry or confirmation email showing that the same job was submitted means stop: tell the user it was already submitted and do not create another application package or proceed with an application. If the user says the tracker is wrong, update it only after they clarify the correct status.
3. If there is a submitted application to the same company for a different job, warn the user and identify the previous role/date before preparing the new materials. You may prepare the resume and application answers, but before an external application is submitted, ask the user to confirm they want to proceed with another application to that company.
4. Read `candidate_summary.txt` without modifying it.
5. Compare the posting's requirements with facts in the summary. Prioritize supported, relevant experience and skills, retain accurate scope and chronology, and use the posting's terminology only where it truthfully describes the candidate. Do not copy unsupported requirements into the resume. If a material requirement or date is unclear, ask the user or omit it.
6. Draft a clean, ATS-readable resume in Markdown, plain text, Word `.docx`, and PDF formats with the same content. The text file should retain standard headings and bullets while omitting Markdown syntax. The `.docx` and PDF should use simple single-column layouts with standard headings and bullets, without tables or graphics. Use concise section names and no keyword stuffing or unsupported claims. Include contact details only if present in the source material. Do not add a cover letter unless asked.
7. Save every generated resume version and its related metadata in the project-root `tailored-resumes/` directory, regardless of where the posting metadata lives. Name the Markdown, text, Word, and PDF files `<company>-<job-title>-tailored-resume.md`, `<company>-<job-title>-tailored-resume.txt`, `<company>-<job-title>-tailored-resume.docx`, and `<company>-<job-title>-tailored-resume.pdf`, using a filesystem-safe slug. For a posting found in an existing jobs file, create a compact sidecar metadata file in `tailored-resumes/` that references the original metadata filename. For a posting supplied only by URL or company/title, save a compact `<company>-<job-title>-job-posting.json` sidecar there with the URL, title, company, job ID when available, retrieval date, and relevant posting details. Keep posting identifiers, source references, and other metadata in JSON only; do not add YAML front matter or metadata headers to the resume. Avoid copying the full job description into the resume.
8. This project runs in WSL and keeps a Windows mirror at `/mnt/c/Users/irekr/Documents/JobMatchAI/tailored-resumes/` (Windows path: `C:\Users\irekr\Documents\JobMatchAI\tailored-resumes`). After writing or revising any resume or its JSON metadata in the project folder, copy the same files to the Windows mirror and create the destination directory if needed. Keep filenames and contents identical in both places. Do not delete older versions from either location.
9. Never overwrite an existing tailored resume without an explicit request. If the target name exists, add a numeric suffix and apply the same versioned filename in both locations. Keep the job metadata unchanged unless the user explicitly asks to update it. Never modify `candidate_summary.txt` unless the user explicitly asks to update the source profile.

## Privacy

Treat the candidate summary, job posting, and generated resume as private personal data. Keep all generated resume versions and related metadata in the project `tailored-resumes/` directory, which must be ignored by Git, and mirror them to the Windows path above. Do not add candidate data or scraped job content to commits, examples, logs, or unrelated files. If the project directory is not already ignored, add `/tailored-resumes/` to `.gitignore` before saving output. The summary is read-only unless the user explicitly asks for a source profile update.

## Completion

Report the Linux project path and Windows mirror path and the posting the resume targets. Briefly note any important requirement left unsupported. Do not reproduce the candidate's personal details in the completion message.

## Application tracking

When the user says they submitted an application using a tailored resume, add or update a record in the Git-ignored `job-applications/applications.json` and mirror it to `/mnt/c/Users/irekr/Documents/JobMatchAI/job-applications/`. Record the company, role, posting/application URL, submission date, resume version and format if known, and status. If Gmail is connected, search for an application confirmation and record its subject, sender, received timestamp, and message link. Do not mark a confirmation as received without finding one. If the exact uploaded file is not stated by the user or confirmed in the message, mark it unknown rather than assuming which prepared file was used. Always consult the tracker and available Gmail history before preparing another application. Never send messages or take follow-up actions unless explicitly requested.
